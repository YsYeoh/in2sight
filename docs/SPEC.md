# in2sight — Design Spec (awaiting owner's final review)

## 1. Goal
One private dashboard to see insights, traffic and basic analysis across the owner's 3–4 Instagram accounts, using Meta's free API.

**Scope v1 (A + B):** per-account trends, cross-account comparison, content analysis (top posts, format comparison, best posting time).
**Also in v1 (owner-approved):** post tags (content pillars) with per-tag analysis, simple flags (post >2× account median reach; reach drop vs previous period), posted-history calendar, **Story capture**.
**Later (C):** AI-written weekly summaries via Claude API. Not designed here beyond leaving the data model ready.
**Out of scope:** posting/scheduling, DMs, comments moderation, other people's/client accounts, Meta App Review, website analytics (GA/UTM).

## 2. Users & constraints
- Single user (owner). One Supabase Auth login; no multi-tenant.
- 3–4 accounts, currently Personal → must be converted to **Creator** (free) first. Personal accounts have no insights API.
- Meta app stays in **Dev mode** (no App Review): works for accounts added as Instagram Testers on the app. This is the whole reason we avoid client accounts.
- Stack fixed: Next.js (App Router, TypeScript) on Vercel; Supabase (Postgres + Auth). **Scheduler (owner decision 2026-10-14):** any HTTP caller hitting `/api/cron/tick` every 30 minutes; recommended **cron-job.org** (free, 1-minute granularity, custom headers, failure notifications, execution history); Supabase `pg_cron` + `pg_net` is the documented fallback. Vercel Hobby cron is once/day, too coarse for Stories, so Vercel Cron is not used.
- Deps (each replaces a lot of code): Tailwind + shadcn/ui, TanStack Table, next-intl, Recharts, GSAP (motion), the audience globe is hand-written canvas 2D (no Three.js; owner decision 2026-10-17), `web-push`, `write-excel-file`, `puppeteer-core` + `@sparticuz/chromium`. No others without a reason.

## 3. Meta API approach
- **Instagram API with Instagram Login** (graph.instagram.com). No Facebook Page needed.
- Permissions: `instagram_business_basic`, `instagram_business_manage_insights`.
- Connect flow per account: "Connect account" → Instagram authorize → callback → code → short-lived token → **long-lived token (60 days)** → store.
- Token refresh: the sync tick refreshes any token expiring within 14 days (retried at most daily) (a successful refresh renews it for another 60 days, so healthy accounts never expire). If refresh fails, mark account `needs_reconnect`. The "token expiring" alert (7d / 2d) therefore only fires when refreshes keep failing.
- History limits: account-level insights reach back a limited window (Meta's insights guide, checked Oct 2026: "User Metrics data is stored for up to 90 days"; individual metrics may reach back less — verify per metric when building the sync, Plan 5). **Connect early and snapshot daily** — our DB is the history.
- Metric names change often (e.g. `impressions` → `views`). Verify against current docs when implementing; keep metric lists in one file.

## 4. Architecture
```
Browser ── Next.js (Vercel) ── Supabase Postgres (RLS, owner only)
                │
   cron-job.org ──► /api/cron/tick (every 30 min) ─► due jobs per account ─► Instagram Graph ─► upsert snapshots
   (fallback: Supabase pg_cron + pg_net)   Stories every tick · post metrics hourly/daily · account day · audience · token refresh
```
- `/api/cron/tick` requires `Authorization: Bearer <CRON_SECRET>` (constant-time compare; fails closed if unset), answers `202` at once and runs the work after the response (Next `after()`) within a time budget; a per-account lease stops overlapping or retried ticks from double-running. Use Supabase **service role** server-side only.
- Dashboard reads via the user session (RLS). Tokens table is **service-role only**, never exposed to the browser.
- Meta client: `lib/instagram/oauth.ts` (auth/tokens) + `lib/instagram/data.ts` (insights reads), thin `fetch` wrappers, no SDK; all metric names in `lib/instagram/metrics.ts`.

## 6. Sync jobs
**Scheduling:** one tick every 30 minutes (see §2/§4); a pure function decides per account which jobs are due from `sync_state`. Work that does not fit the tick's time budget stays due for the next tick.

**Lanes (Plan 11a):** each tick first runs the regular jobs (Stories, recent post metrics, daily refresh, token refresh) for every account with a small slice (8 s), then splits the remaining budget equally across accounts that still have work (a new account's onboarding, the history import, regular work a slice cut short). An app-wide rate limit stops the tick before lane 2; a pass that stops on its time budget starts a continuation pass.

**Onboarding / history import (Plan 11a):** a new (or reconnected) account is imported newest first so Overview fills within minutes: profile + follower snapshot and live Stories → the newest 7 days of account insights (newest first) → post list → metrics for recent posts and the newest 10 older posts → audience → days 8–90, newest first → metrics for the remaining older posts (later plans add cover images and comments here). Progress is written to `sync_progress` (best-effort, throttled) and shown on Accounts and Overview; analysis marks windows that are still importing instead of comparing them.

**Stories job (every tick):** for each `active` account, list live Stories, upsert into `media`, insert a `media_metrics` snapshot per story. Stories exist for 24h only, so a missed window is lost data; a 30-minute tick gives ~48 snapshots per story.

**Capture extras (Plan 11b):** every optional Meta metric or field is a SEPARATE, non-fatal call made after the core snapshot is stored (one unsupported metric fails a whole batched request); an "unsupported" answer is remembered in `sync_state.capabilities`, transient errors are not. Story job, after the snapshots: cover copy on first sight (URL from the listing; retried every pass while live, then `unavailable`), then Story extras (follows, profile visits, profile activity) every 2 h of the Story's life and in its last hour. Media metrics: after the core loop, feed/carousel extras (follows + profile visits, profile activity) and Reels extras (watch time, skip rate) within 20 extra calls per account run; plus a 7-day checkpoint snapshot. Lane 2 only, after the history import: `covers` (hourly, 25 posts/Reels per run, newest first, fresh URL per item, CDN allowlist + 5 MB + image types + 10 s, back-off then `unavailable`) and `comments` (hourly, only with the granted `instagram_business_manage_comments` scope — Meta returns an empty list without it — posts of the last 30 days whose comment count changed, ≤ 20 page calls per run). Raw account-insights and audience bodies are archived to `api_snapshots` (deduped, best-effort). Covers are served only by the owner-only route `GET /api/media/[id]/cover`; a permanent account delete removes the account's objects.

**Daily job:** for each `active` account: fetch followers + yesterday's account insights → `account_daily`; list new media → `media`; fetch insights for posts <30 days old → `media_metrics`; fetch audience + online_followers (if ≥100 followers) → snapshots. One account failing must not stop the others; log per-account result, flip status on auth errors. `archived` accounts are skipped by every job. After the daily and Stories jobs finish, the alert rules (§7c) are evaluated and push notifications sent.

## 7. Analysis (v1, plain SQL/TS — no ML)
- **Growth:** 7/30-day follower and reach deltas per account.
- **Top/bottom posts:** by reach and by engagement rate ((likes + comments + saves + shares) ÷ reach, see below).
- **Format comparison:** avg reach + engagement by `media_type` (Reel / carousel / image).
- **Best time to post (approved: both, with a sample guard):** default view = **followers online** by weekday × hour (`online_followers`, needs 100+ followers). A toggle shows **your post performance** (avg engagement rate by weekday × hour of `posted_at`); cells with fewer than 2 posts are greyed out, and the view shows "Needs ~30+ posts for a reliable pattern" until the account has ≥ 30 feed posts.
- **Cross-account:** same metrics side by side.
- Pure functions in `lib/analysis/*`, unit-tested.

**Metric definitions (defaults):**
- *Engagement rate* (post) = (likes + comments + saves + shares) ÷ reach. Account ER over a period = Σ interactions ÷ Σ reach.
- *Delta* = value vs the comparison window of the Time Scope (§7b): by default the immediately preceding period of equal length (a calendar month/quarter/year is compared with the previous one, always cut to the same number of days counted from its first day, so sums stay comparable: a running 1–17 Oct vs 1–17 Sep, a finished September vs 1–30 Aug; a comparison is never longer than the current window); or the same period last year, custom days, or nothing. A comparison is shown only when at least 80 % of its days have data; otherwise the value shows with "not enough history".
- *Net follower change* = follows − unfollows; *followers* = daily snapshot.
- *Story exit rate* = exits ÷ story views.
- *Post taking off* = reach ≥ 2× the median reach of the account's previous 20 feed posts, evaluated ≥ 24 h after posting; needs ≥ 5 prior posts.
- *Daily boundaries* follow Instagram's insight day; displayed in the user's timezone. Verify the exact boundary behaviour against Meta docs at implementation.

## 7b. Functional design (approved)
- **Flows:** Connect → Overview (glance) → Account detail (dig in) → Compare.
- **Grouping is optional.** An account may have a `group_name` or none. Ungrouped = isolated: it gets its own card and is never compared with others unless the user widens scope to "All accounts".
- **Overview:** per-account status cards (followers, reach, engagement, posts + change vs previous period), listed under group headings; isolated accounts listed together. The shared Time Scope bar (below) sets the page's range.
- **Time Scope (Plan 12a):** one bar on Overview, the account pages (not Audience) and Calendar; the URL is the only state: `?from=7d|14d|30d|90d|6m|1y|ytd|all` (a rolling preset) or `?from=YYYY-MM-DD&to=YYYY-MM-DD` (fixed days), `cmp=none|yoy` (default: previous period) or `cfrom/cto` (custom comparison days), `gran=day|week|month` (default automatic: day up to 92 days, week up to 400, then month); the pickers submit `week=<any day>`, `month=YYYY-MM`, `quarter=YYYY-Qn`, and old `?period=7|30|90` links still work. Default: last 30 days vs the previous 30. Days are owner-timezone days (DST-safe). Rolling presets end on the latest settled day (Instagram's lag); fixed ranges are cut there. 6 months = 182 days, 1 year = 365 days, "all" = from the first captured day, at most about 5 years (1,830 days, also the cap of any custom range), never compared. A note says where the data starts when the range or the comparison begins before it. Posts and Stories tabs, the format comparison and the Calendar follow the scope; best-time heatmaps keep all stored posts and the last 30 days of followers online; Stories are capped at 200 per account per range (the tab says so). Internal links (tabs, account cards, back/calendar links, the Overview and Calendar nav items) keep the scope.
- **Compare / ranking:** scoped to a group by default; toggle to all accounts; user picks the metric and accounts.
- **Rules:** one timezone (owner's); numbers always shown with a comparison; missing data states why (e.g. "needs 100+ followers"); "last synced" shown per account.
- **Not in v1:** goals/targets, scheduled or emailed reports, shareable report links, custom report builder (the Explorer, §7e, is a whitelisted analysis view, not a free-form builder), logo upload.

## 7c. Alerts & account lifecycle (approved)
**Alerts: in-app + Web Push.** Rules run after each sync job. Defaults (adjustable in Settings): token expiring (7d, again at 2d), needs reconnect, sync failing (2 consecutive failed runs), reach drop (7d reach ≤ −20% vs previous 7d, 7-day cool-down), post taking off (≥ 2× account median reach). Push on for all except "taking off". Adjustable in Settings → Notifications (stored in `profiles.alert_settings`): push on/off per type, reach-drop % (5–90), taking-off multiple (1.5–10), sync-failing streak (1–10); the token stages (7d/2d) and the 7-day reach-drop cool-down are fixed. Each alert has a `dedupe_key` so it never repeats; `notifications.payload` holds i18n parameters only, the text is rendered from the message catalogs (push text in the owner's profile language). Delivered to the notification centre (bell + badge) and to subscribed devices via `web-push` + VAPID keys. Push permission is requested only from an explicit "Enable notifications" action. iOS needs the PWA installed to Home Screen.

**Remove account = archive.** Status → `archived`, syncing stops, account hidden from all views, **history kept**. Reconnecting the same `ig_user_id` restores it and continues the history with no gap. A separate, confirmed "Delete all data permanently" action hard-deletes an archived account's rows (cascade).

**Backfill on first connect** (defaults, Plan 11a order): account insights for the last 90 days, imported newest first (the newest week before everything else); all media up to 500 posts with their current lifetime metrics, newest first; no Story history (not retrievable). Reconnect and "Sync now" resume an unfinished import; they never restart it.

## 7d. Exports & reports (approved: Excel + PDF)
- **Excel:** server route `/api/export/xlsx` (auth required) using `write-excel-file` (not `xlsx`: known vulnerabilities in the npm build). Sheets: Summary, Daily, Posts (+tags), Stories, Audience, Tags. Real date cells formatted per the user's date-format setting; headers localized (en / zh-CN). Exports use the page's Time Scope (Plan 12a, strictly allow-listed parameters); file names are `in2sight-<scope>-<from>_<to>`; the Summary sheet states each account's KPI days and comparison days.
- **PDF:** a print-optimized Report page per account and for the Overview (A4, always light). `/api/export/pdf` renders that page with headless Chromium (`puppeteer-core` + `@sparticuz/chromium`) handing it the report data over the DevTools protocol (the print page itself has no data access; owner decision, Plan 9). Bundled Noto Sans SC subset for Chinese. One layout, no second PDF renderer.
- **Report options:** section checkboxes (KPIs+deltas, reach/views trend, top posts, format comparison, tag performance, best time, audience, Stories summary, flags), title, optional note. No logo upload in v1.
- **Ceiling:** Chromium cold start adds seconds to the first PDF after idle; if volume grows, move PDF generation to a small dedicated service.

## 7e. Explorer, rollups and drill-down (Plan 12b; creator-toolkit design §0b)
- **Rollups in SQL, not TypeScript** (`supabase/migrations/20261024000001_explorer.sql`): `explorer_daily` (account days per account or per day/week/month bucket; followers = last value per account, summed), `explorer_media` (media published in a range with their latest snapshot, owner-timezone day/weekday/hour; also the single-posts list, newest 500), `explorer_posts` (the same summed per account/format/tag/weekday/hour/bucket; "measured" = reach > 0; engagement parts never include Stories) and `explorer_followers` (last follower count per owner-timezone hour or day from `follower_snapshots`). All `security invoker` (RLS applies), `set search_path = ''`, execute for `authenticated` only; they return additive parts, one row per group. No rollup tables: measured ≤ 0.3 s for 10 accounts × 2 years. The read policies of `account_daily`, `media`, `media_metrics`, `media_tags`, `follower_snapshots` use `(select public.is_owner())` so the check runs once per query.
- **Registry** (`lib/metrics.ts`): each metric has a source (`daily` = account insight days; `posts` = published media) and computes its value from the parts; a new metric = one entry. Dimensions: group, account, format, tag, weekday, hour, time (the Time Scope granularity), single posts. Account totals group by group/account/time only and cannot be narrowed to a format, tag, weekday or hour. Every id in the URL is allow-listed (`lib/explorer/state.ts`); the server maps a state to fixed RPCs — no free-form queries.
- **Explorer** (`/explorer`): metrics (≤ 4), break-down, filters (accounts, group, format incl. Stories, tag/untagged, weekday, hour), Time Scope bar, linked chart (one metric + the comparison period) and table (all metrics with change), saved views (`explorer_views`), Excel export of the current view (`/api/export/explorer`, strict canonical query, `Server-Timing`).
- **Explorer days and limits:** days follow the KPI cards, but a rolling range ends on the OLDEST settled day among the accounts in scope whose sync is within the 3-day lag window (an account synced longer ago, or never, is ignored so it cannot pull every window back), so one lagging account never shows as a dip. Daily grouping over a range longer than 900 days is shown weekly (PostgREST returns at most 1,000 rows per call). The comparison over time is drawn only for buckets that are complete in both periods (a partial first or last week or month shows no change). The best-time heatmap drill-down and every posts list under the preset "All" list all stored posts (up to 5 years, newest 500).
- **Drill-down:** group → accounts → formats → single posts → the item level (latest numbers, follower curve around the post, that day's followers/non-followers reach of its format); weekday → hours; a time bucket → that bucket as fixed days, one granularity finer. Breadcrumb `All accounts › group › @account › format › post`; every link keeps the Time Scope. Entry points: Overview tiles, group headings, comparison rows and chart; account format comparison, "your post performance" cells, Posts table.
- **No hourly reach:** Instagram's account insights are daily; hour/weekday mean the publishing time; the only intraday series is the follower count.

## 7f. Post Lab (Plan 13b; creator-toolkit design §5)
- **Route** `/accounts/[id]/media/[mediaId]` for posts, Reels, carousels and Stories of a live account (another account's media id, an archived account or a bad id → 404). Header: cover, format, account, owner-timezone date and time, Live / Expired / "no longer on Instagram", the whole caption, editable tags, Instagram link, a link to the Explorer item level (follower curve). The back link and every link keep the Time Scope it was opened with; `?peers=90` and `?er=followers` are its own URL state.
- **Peers** = the account's posts of the same format published before this one, newest first: 30 (default) or 90. **Sample guard** = 5 peers that have the number (`MIN_PRIOR_POSTS`, the "taking off" rule's). **Percentile** = mid-rank among the peers; difference vs median relative for counts, in points for rates.
- **Scorecard** (latest KNOWN value of each number — `post_lab_latest`): reach, views, interactions (feed: likes + comments + saves + shares; Stories: Instagram's total), engagement rate per reach (default) or per followers on the posting day (`account_daily.followers`), save rate, share rate, follows per 1,000 reach, profile visits, link taps (`profile_activity` BIO_LINK_CLICKED); Stories add replies, Reels a watch-time panel (average, total, skip rate — lower is better). A missing number always has a reason (not reported for this format / not captured / not measured / under 5 viewers / no reach / no follower count), never 0.
- **Verdict** (reach vs the peers): Breakout ≥ 2× median, Above typical ≥ 75th percentile, Below typical < 25th, else Typical; Too early under 24 h, and between 24 h and day 7 unless the post already leads (reach only grows); a Story gets the full scale once expired. No verdict below the guard, without reach, or for a Story under 5 viewers.
- **Velocity**: cumulative reach and views at 1 h ± 30 min, 6 h ± 1 h, 24 h ± 2 h, 48 h ± 3 h, 7 d ± 12 h (Stories 1 h, 6 h, 24 h) — the snapshot nearest each mark inside its window (`post_lab_points`), next to the peers' median at the same age (≥ 5 peers per point). A checkpoint without a snapshot is a gap, never interpolated.
- **Stories**: navigation funnel (forward, back, exit, swipe; count and share of views) + replies; the day's Stories in order with reach vs the first measured one and exit rate (exits ÷ views); best/worst frame from 2 measured frames.
- **Caption lab**: characters, hashtags (list), mentions, emoji, question, call-to-action words (en + zh list); median reach with vs without each trait over the peers read (same format, ≤ 90), only from 20 measured posts and 5 per side — a pattern, not a cause. **Similar posts**: up to 6 peers, shared tags first.
- **SQL** (`supabase/migrations/20261026000001_post_lab.sql`, applied to the live project 2026-10-19; in a fresh environment apply it before the code): `post_lab_latest(ids)` and `post_lab_points(ids, marks, tols)`, `security invoker`, `set search_path = ''`, execute for `authenticated` only; the checkpoint table is passed in from `lib/analysis/post-lab.ts`. Without them the route says "needs a database update". Everything else is owner-session selects. Pure analysis: `lib/analysis/post-lab.ts`, `lib/analysis/caption.ts`.
- **Entry points**: the Posts grid/table (flask link) and the post drawer ("Open Post Lab"), the Stories filmstrip and the Story drawer, the Calendar day list, the Explorer item level.

## 7g. Growth tab (Plan 15a; creator-toolkit design §6 "Audience & growth")
Status: code complete, pushed to `main` (2026-10-22), NOT verified live (`docs/RUNBOOK_GROWTH.md`). No migration, no new table, no sync or Meta change: the tab reads existing tables with the owner session.
- **Tab and range:** `?tab=growth`, beside Overview / Posts / Stories, with the range bar (`RangeBar` `keep={{ tab: 'growth' }}`: a range change stays on the tab). Loaded only when opened.
- **KPIs** (six cards with sparklines): Followers and Net follows are the account Overview's KPIs (same window and comparison); Follows, Unfollows and Churn rate share Net follows' comparability (no comparison, same reason, whenever Net follows has none); Non-follower reach compares only when both windows have breakdown rows on at least 80 % of their days. Churn = Σ unfollows ÷ the follower count at the window start (lower is better).
- **Followers:** `account_daily.followers` (daily); hourly points for ranges of 7 days or less (`explorer_followers`). Change over the range (absolute and %). Instagram has no follower history, so the history starts on the connect day and the card says so. **Projection** 7 / 30 / 90 days: Theil–Sen median slope of the daily counts of the latest 28 days (at least 14, else "not enough history"), band = 25th–75th percentile of the pair slopes, rounded to the band's precision, confidence Low or Medium only; the card states method, sample, dates and the per-day rate.
- **Follow flow:** follows vs unfollows per day from Instagram (`netSource` `instagram`); a day without them (Instagram gives none under 100 followers) uses the change of the follower count (`derived`, net only); the card says `instagram` / `derived` / `mixed`. Churn, best and worst days, and "what was published that day" (posts and Stories of the owner-timezone day) in the tooltip. The follows / unfollows mapping (`FOLLOW_TYPE`) is UNCERTAIN and must be checked first (RUNBOOK_GROWTH §2).
- **Loyalty vs discovery:** reach by follow type (`account_daily_breakdown`) over time and per format, summed over formats (a person reached by a Story and a Reel counts twice; said on screen).
- **Audience then vs now:** the first and the latest `audience_snapshots` inside the range (age, gender, countries, cities; top 8 of "now"); a change of 2 points or more with at least 100 people in both snapshots is highlighted; a key outside "then"'s top 45 has no "then" ("—", never 0).
- **Unusual days:** a day's net follows or reach against the same weekday of the 8 weeks before it (at least 4 values), modified z-score |z| of 3.5 or more and a move of at least max(3, 10 % of typical); at most 10 per range, most extreme first.
- **"Why did this change?"** (`lib/analysis/why.ts`, run in the browser on the model's per-day facts): six rules (a post of that day or the day before, no posts, Story reach, non-follower share, time of day, comments), each with evidence, n and a confidence word (Low or Medium, never High); reasons pointing the other way are dropped; at most 4; always labelled "Patterns, not proof".
- **URL state:** `?day=YYYY-MM-DD` (a day inside the range) and `?why=reach` (default net follows), written with `history.replaceState` (no server round trip); a range change drops both; a chart click picks a day only when the chart is daily, the Unusual days list is the keyboard path.
- **Reads:** owner session only, no SQL; the breakdown, Story and comment reads are capped (Story and comment counts: newest 5,000 each, a capped read says from which day counts are complete and older days are unknown, never 0). Pure analysis: `lib/analysis/trend.ts`, `lib/analysis/why.ts`, `lib/dashboard/growth.ts`.

## 8b. Frontend architecture (owner rules)
1. **Reuse.** shadcn/ui primitives in `components/ui/`; our shared pieces in `components/shared/` (`AppShell`, `DataTable`, `StatCard`, `ChartCard`, `EmptyState`, `PageHeader`). Inline first, extract on the second use. Pages hold wiring only; logic is pure functions in `lib/`.
2. **Flexible, with a limit.** One metrics registry `lib/metrics.ts` (key, i18n label key, formatter, aggregation, source) drives cards, charts, tables and pickers. Feature folders: `features/overview|account|accounts|tags`. No plugin systems, no generic dashboard builder.
3. **i18n.** next-intl, `messages/en.json` + `messages/zh-CN.json` (Simplified `zh-CN`, approved). No hardcoded UI strings; a test fails on missing keys. New language = one JSON + one entry in the `locales` list. `Intl` for dates/numbers. Server returns error keys, UI translates. CJK-safe font stack.
4. **Themes + light/dark.** Semantic CSS-variable tokens (`--background`, `--primary`, `--chart-1..6`); never raw colors in components. A theme = one CSS block with light + dark variants (`data-theme` + `data-mode` attributes on `<html>`, `data-mode` being `light` / `dark`; the preference may be `auto`, resolved on the device before first paint, Plan 16a). The choice lives in a cookie and is applied to `<html>` attributes on the server (no flash, no extra dependency). Charts read the same tokens. Ship 4 themes at launch (Ink, Sunset, Forest, Mono — approved); check chart-color contrast per theme. Corner radius is also a token (Sharp/Soft/Round, default **Soft** 8/12/16).
5. **Responsive.** Mobile-first; must work on phone, tablet, desktop and ultra-wide. Breakpoints 640/768/1024/1280. Sidebar → bottom tab bar (phone) → icon rail (tablet) → full sidebar (desktop). Tables → card lists on phone; dialogs → bottom sheets; date-range picker → sheet. `@media (pointer:coarse)` forces ≥40px touch targets. Content max-width ~1600px, centered. Heavy motion (globe, particles) is off on phones, `prefers-reduced-motion`, and Save-Data.
6. **PWA.** Installable (`app/manifest.ts`, icons, `theme_color` follows theme: the `<meta name="theme-color">` carries the user's theme + mode background; the cookie-less manifest uses Ink light). Small hand-written service worker: cache static assets + offline fallback page. **No authenticated data is cached by the SW** (shared-device safety). The same service worker handles Web Push (§7c).
7. **Formats are user settings** (stored in `profiles`, cached in a cookie to avoid flash): date format (`YYYY-MM-DD` / `DD/MM/YYYY` / `MM/DD/YYYY` / `D MMM YYYY`), time format (12/24h), week start (Mon/Sun), timezone, number format. All dates/numbers go through one `lib/format.ts`; no inline `toLocaleDateString`.
8. **Loading feedback and navigation speed (Plan 10, creator-toolkit design §3).** One loader, the Insight Orb (`components/shared/InsightOrb.tsx`: SVG + CSS keyframes in `styles/loading.css`, colours from `--chart-1..3`, sizes xs/md/lg, reduced motion = slow opacity pulse, `role="status"` + hidden label). A top progress bar (`NavigationProgress`) runs for every client navigation (link clicks, tabs, GET filter forms) and completes when the URL changes (failsafe timeout); nav items show the orb while their link is pending (`NavLink`), action buttons while their action runs (`LoadingButton`). Every page segment has a page-shaped `loading.tsx` (test-enforced; the accounts list lives in the `(list)` route group so `/accounts/[id]` gets its own). The account page streams its tab in `<Suspense>`; the layout streams the notification bell. Server: the owner check and the accounts / sync-status reads are per-request singletons (`React.cache`); the proxy sends `Server-Timing: auth;dur=…, proxy;dur=…`. Budgets: click → feedback ≤ 100 ms; skeleton ≤ 300 ms; warm page data ≤ 1.2 s p75 (`docs/RUNBOOK_PERF.md`).
9. **App-shell tabs (Plan 14c; UX polish design §4.3).** The top window is the shell only (sidebar, header with the tab strip, phone bottom bar); every tab is a same-origin `<iframe>` of the app kept alive while hidden (`invisible` + `inert`; 8 live frames, 3 on touch devices, least recently viewed discarded and reloaded from its URL). The `(app)` layout serves both faces: `AppShell` renders the page without chrome when `window.self !== window.top` (the request's `Sec-Fetch-Dest: iframe` is only the first-paint hint; a refresh or server action re-renders the layout without it). All tab logic is the pure reducer `lib/tabs/model.ts`; the shell, its frames and the service worker talk only through the validated messages of `lib/tabs/protocol.ts` (same origin, sender checked, tab-page URLs only, `targetOrigin` never `*`). Back/Forward are per-tab stacks kept by the shell (the browser has one history for all frames). Any non-tab page shown in a frame (login, 2FA, setup, sign-out, report) replaces the whole window (`FrameBreakout`, root layout). Every route sends `Content-Security-Policy: frame-ancestors 'self'`. The open tab list lives in `localStorage` (`in2sight.tabs`), the address bar shows the active tab. Preference changes (theme, mode, language, formats) are broadcast between the app's documents on a same-origin `BroadcastChannel` (`PrefsProvider`), so every tab follows.
