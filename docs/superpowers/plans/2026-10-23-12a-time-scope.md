# Plan 12a: Time Scope — one shared range/compare/granularity filter instead of 7/30/90 — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Replace the fixed 7/30/90-day `PeriodSelect` with the shared **Time Scope** of the approved design (presets 7d/14d/30d/90d/6m/1y/YTD/all, custom date range, week/month/quarter pickers, compare to previous period / same period last year / custom days / nothing, granularity auto/day/week/month), kept in the URL and used by Overview, the account pages and their tabs, Calendar and the Excel/PDF exports — with owner-timezone, DST-safe days, null-safe bucketing, a data-coverage note, and reads that no longer silently stop at 200 days or PostgREST's 1000-row cap.

**Architecture:** A pure library `lib/time-scope/` turns the URL (`?from&to&cmp&gran`, plus picker shorthands and old `?period=` links) into a `TimeScope`, and a `TimeScope` + today + the first captured day into a `ResolvedScope` (KPI window, covered days, comparison days, effective granularity, coverage flags). Day maths stays on `'YYYY-MM-DD'` strings (`lib/sync/time.ts` `addDays`, never `Date` arithmetic across DST); the only day→instant conversion is `dayStart()` for `posted_at` bounds. `summarize()` in `lib/analysis/growth.ts` generalises from "period days" to a window (`{ last: n }` = the old rolling behaviour, or fixed days) with a comparison mode; `lib/analysis/buckets.ts` sums/levels daily rows into day/week/month buckets and marks partial ones. Loaders page through `.range()` (owner session, RLS) from the scope's first needed day. One client component, `TimeScopeBar`, renders presets as links, compare/granularity as GET-form selects and the pickers as GET forms inside a `ResponsiveDialog` — the URL is the only state, so the top progress bar and route skeletons keep working unchanged. Exports take the same parameters (strictly allow-listed) and put the range into file names and sheets.

**Tech Stack:** Next.js 16 App Router (server pages, client components), TypeScript strict, `@supabase/supabase-js` (owner session only), next-intl 4, shadcn/Radix (`Button`, `Dialog` via `ResponsiveDialog`), recharts 3 (unchanged), Vitest 5 + Testing Library + jsdom 29. **New dependencies: none** (a date library is not needed: day strings + `lib/sync/time.ts` + `Intl` already cover owner-timezone days and DST; native `<input type="date">` and `<select>` cover the pickers).

**Spec:** `docs/superpowers/specs/2026-10-15-creator-toolkit-design.md` §0b bullet "Drill-down & time scope (owner, 2026-10-16)" (approved design), §0b Round 3/4 (desktop-first, more than 4 accounts soon, own accounts only), §8 (cross-cutting rules); `docs/SPEC.md` §7 (metric definitions, "Delta"), §7b (Overview, "one date-range switch"), §7d (exports). Project rules: `CLAUDE.md` (binding).

**Dry run:** see "Dry-run result" at the end of this file.

## Decisions taken in this plan (owner: please confirm the ones marked ⚠)

- **Default = last 30 days vs the previous 30 days, automatic buckets** (spec/SPEC §7b say 30). The default scope serialises to NO parameters, so every existing bare link (`/overview`, `/accounts/<id>`) keeps meaning the same thing.
- **URL format** (compact, human-readable, bookmarkable; the spec's four keys): `from=7d|14d|30d|90d|6m|1y|ytd|all` for a preset, `from=YYYY-MM-DD&to=YYYY-MM-DD` for fixed days, `cmp=none|yoy` (previous period is the default), `cfrom=…&cto=…` for custom comparison days, `gran=day|week|month` (auto is the default). Picker forms submit shorthands that are accepted as input only: `week=<any day of that week>`, `month=YYYY-MM`, `quarter=YYYY-Qn`; old `period=7|30|90` links map to the matching preset. Links the app builds always use the canonical form. Why: a preset stays rolling when bookmarked ("last 30 days" next month is still the last 30 days), fixed days stay fixed, and the plain GET-form shorthands make the pickers work without client-side date code.
- **Rolling presets keep today's exact behaviour:** 7d/14d/30d/90d/6m (= 182 days, 26 weeks)/1y (= 365 days) measure the last N days ending on the account's latest settled day (Instagram's up-to-48 h lag, `MAX_LAG_DAYS`), compared with the N days before. All existing 7/30/90 tests stay green unchanged.
- **Fixed ranges** (custom days, week, month, quarter, YTD, all) measure their days up to the latest settled day, so a running month (1–17 Oct) is never compared as if it were complete.
- **"Previous period"** = the same calendar unit before for whole months (a month → the previous month, a quarter → the previous quarter, Jan–Dec → the previous year), otherwise the same number of days immediately before (a week → the previous week). **"Same period last year"** = the same days one year earlier (29 Feb → 28 Feb; a month end stays a month end). Every comparison window is cut to the current window's length from its start, so 1–15 Oct compares with 1–15 Sep (never with all of September) and the existing "comparable only at ≥ 80 % coverage" rule applies to any comparison unchanged.
- **Comparison partly outside coverage:** no new rule. The comparison is shown only when its window has ≥ 80 % of days with data (the existing `MIN_COVERAGE`; while importing it must be complete); otherwise the KPI shows its value with "Not enough history to compare yet". The scope bar adds one sentence when the range or the comparison starts before the first captured day ("data from …").
- **`all` = from the first captured day to today, capped at `MAX_DAYS` = 1,830 days (≈ 5 years); it is never compared** (there is no earlier period). The same cap bounds every custom range (a longer one keeps its end), so the largest daily read is ≈ 2,200 rows per account (two 1,000-row pages plus a short one).
- **Auto granularity:** day up to 92 days, week up to 400 days (so 6 months and 1 year chart weekly), month above. A manual choice always wins. Weeks start on the owner's week-start preference; a bucket the range starts or ends inside is marked partial (`*` on its label, explained under the chart). Sums (reach, views) add the days that have data and stay `null` (never 0) when none does; followers take the last value in the bucket.
- **Scope across pages:** the URL is the only state. Links that already exist carry the current scope: account tabs (they used to DROP `?period`), Overview account cards → account page, account "back" → Overview, account → Calendar, the Posts filter form, the export dialog, and the main navigation's Overview and Calendar items (AppShell reads the current URL with `useSearchParams` and appends only the scope keys). Pages without dates (Accounts list, Tags, Settings) get plain links.
- ⚠ **Posts and Stories tabs follow the scope.** Default 30 days: the Posts tab used to list every stored post (newest 500) and the Stories tab the last 14 days. "All" restores the long list. The post count line keeps saying "Showing X of Y posts".
- ⚠ **Calendar without scope parameters still opens on the current month** (its old default); with a scope it shows the scope's days as whole weeks (days outside the scope dimmed) and its arrows step one period (a month steps by months). Old `?month=YYYY-MM` links keep working (they are the month picker's shorthand).
- **Format comparison follows the scope** (posts published in the range); the best-time heatmaps stay on all stored posts and the last 30 days of followers-online (they need sample size, and Instagram keeps only 30 days of online followers). The Audience tab shows the latest snapshot and hides the scope bar.
- **Flags stay "right now" signals:** reach drop is always last 7 vs previous 7 days (alert rule); "taking off" uses the rolling preset's days (as before) and 7 days for fixed ranges.
- **Reads:** `loadDaily` pages through `.range()` from `readFrom(scope)` to today (oldest first); post reads go newest first until they have both the newest 500 (flags and heatmaps need them) and every post back to the scope's first day; Calendar media reads page up to 5,000 items and keep the existing "too many items" notice; all reads stay on the OWNER SESSION client under RLS. `DAILY_LIMIT` is removed.
- ⚠ **Stories keep a cap of 200 per account per range** (`STORY_LIMIT`; each Story carries up to ~48 snapshots, so a year of Stories would be several MB). The Stories tab now SAYS when it is capped ("Showing the newest 200 Stories in this range"); the export's Stories sheet has the same cap. A per-Story "final numbers" rollup in Plan 12b removes it.
- **Exports use the page's scope:** the dialog shows the scope it will export (changed with the bar), the request carries the canonical scope parameters, the server allow-lists them strictly (`bad_params` for junk, repeated keys or shorthands; old `period=7|30|90` still accepted; no range parameter = the default 30 days), file names become `in2sight-<scope>-<from>_<to>.<ext>`, the Summary sheet gains "Compared from/to" columns, and the PDF report states both windows.
- **No SQL migration.** Paged reads over the existing tables are enough for 12a; rollups belong to Plan 12b.
- **New dependencies: none.**

## Global Constraints

- Ponytail: smallest thing that works; no abstraction with one implementation (the one shared helper, `readPages`, has five callers); **no new dependencies**.
- TypeScript strict. No Meta metric names are added or changed.
- **No migration.** Never edit applied migrations.
- Reads: OWNER SESSION client (`createServerSupabase`) only, under RLS; never the admin client, never `account_tokens`; explicit column lists; fixed error messages (`dashboard read: <op> failed`) that never echo Supabase errors. Page size 1,000 = PostgREST's default `max-rows` (a page shorter than that is the last page).
- Pure logic deterministic: everything in `lib/time-scope/` and `lib/analysis/` takes `today`/`now`/`tz` as inputs; no `Date.now()` / `new Date()` there. Day arithmetic only on `'YYYY-MM-DD'` strings (`addDays`, `addMonths`); instants only via `dayStart(day, tz)`.
- URL parsing never throws; hostile/malformed values fall back to the default part; exports are stricter (`bad_params`).
- Every UI string via next-intl, new keys in BOTH `messages/en.json` and `messages/zh-CN.json` (real Simplified Chinese, full-width punctuation); `tests/messages.test.ts` enforces key and placeholder parity. Backend returns keys, never prose.
- Dates, times and numbers only via `lib/format.ts` (`formatDay`, `formatMonth`, `formatNumber`, …); never `toLocaleDateString`/`toLocaleString`.
- Theming: semantic tokens only (`bg-card`, `text-muted-foreground`, `border-input`, `--chart-n`); no raw colours.
- Responsive 360 / 768 / 1280, desktop-first density; CSS breakpoints only (no `matchMedia`/`useMediaQuery` for layout); `min-w-0`/`flex-wrap` on rows of controls; no fixed pixel widths on layout containers.
- UI kit: build from `components/ui/` + `components/shared/`; dialogs use `ResponsiveDialog*`; density is un-layered (`h-*`/`p-*` on shadcn `Button`/`Input`/`Card` are ignored — use the `--ctl` tokens as the existing selects do); no `npx shadcn` call is needed in this plan.
- Accessibility: presets are links with `aria-current`, selects and date inputs have labels, the dialog is keyboard-operable (Radix), status text uses `role="status"`.
- Tests: Vitest timeout 20 s; jsdom `Blob` has no `.stream()` (build `Response` bodies from strings); rerun once on "worker start timeout" before concluding anything.
- `npm run check` passes after every task. Commits: conventional, `git add` specific paths, `git commit -m "<msg>" -m "Co-Authored-By: Claude Sonnet 5.5 <noreply@anthropic.com>"`. Don't push.

## Review Focus

1. **DST and timezone days:** a custom range crossing a DST change in the owner's timezone reads exactly the owner-timezone days (no lost or duplicated day at the boundary) — Task 5 "posted_at bounds come from dayStart in the owner's timezone (a range across the DST change)"; Task 1/2 day maths is string-only.
2. **The old 7/30/90 numbers do not move:** rolling presets reproduce `summarize(rows, posts, period, …)` exactly — Task 4 "a number is the old rolling window" + every existing `analysis-growth`/`analysis-coverage`/`dashboard-overview` test unchanged.
3. **No silent truncation for 1 year / all:** daily and post reads page past 1,000 rows — Task 5 "pages past 1,000 rows" tests; Stories say when capped (Task 9).
4. **Hostile URLs:** junk, repeated, reversed, out-of-range, future and over-long values never throw and never reach a query unvalidated — Task 2 "hostile or malformed values"; exports reject them — Task 12.
5. **Running periods are not compared as if complete:** a month in progress compares with the same days of the previous month — Tasks 1, 2, 4.
