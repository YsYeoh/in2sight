# Plan 16b: Security (change password, forgot / reset password, sign out other devices) — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. Parallel worktree agents: read `docs/superpowers/implementer-rules.md` first.

**Goal:** The owner can (1) **change the password** in Settings → Security (current + new + confirm, strength meter, show/hide toggle), after which every OTHER device is signed out; (2) **sign out every other device** with one button (Supabase Auth cannot list the current user's sessions, so there is no session list: see Decisions); (3) **reset a forgotten password**: "Forgot password?" on the login page → `/login/forgot` (email, always the same generic answer) → Supabase recovery email → `/auth/confirm` (a "Continue" button, so mail scanners cannot burn the link) → recovery session (aal1) → the EXISTING 2FA step `/login/verify` → `/login/reset` (new password + meter) → every session signed out → `/login` with "Password changed, sign in again". A recovery session at aal1 reaches no owner page and no owner data (the proxy, `requireOwner()` and `is_owner()` already guarantee it; this plan adds tests that prove it for the new routes).

**Architecture:** Pure rules in `lib/auth/password-rules.ts` (`passwordStrength`, the form state types) and `lib/auth/attempts.ts` (a cookie attempt counter: friction, not a security boundary). Supabase calls in two small modules taking a client: `lib/auth/recovery.ts` (`isValidEmail`, `isTokenHash`, `requestPasswordReset` with a fixed minimum duration, `confirmRecovery` via `verifyOtp({ type: 'recovery', token_hash })`, `hasRecentEmailProof` on the verified JWT `amr` claim, `hasRecoveryProof`) and `lib/auth/password.ts` (`changePassword`: re-authenticates the CURRENT password with a separate, non-persisting client, revokes that check session at once, then `updateUser` on the owner session, then `signOut({ scope: 'others' })`; `setNewPassword` for the recovery flow, then `signOut({ scope: 'global' })`). Server actions (`requireOwner()` first wherever a session is required): `app/(app)/settings/security-actions.ts`, `app/login/forgot/actions.ts`, `app/auth/confirm/actions.ts`, `app/login/reset/actions.ts`; `app/login/verify/actions.ts` sends a fresh recovery session to `/login/reset` instead of `/overview`. Route policy: exactly two new signed-out paths (`/login/forgot`, `/auth/confirm`), `/auth/confirm` reachable in every signed-in state like `/auth/signout`, `/login/forgot` joins the entry pages; `/login/reset` gets NO exemption (signed-out → `/login`, aal1 with 2FA → `/login/verify`). UI: `PasswordInput` (show/hide), `PasswordForm` (meter; used by both Settings and the reset page), `SignOutOthersButton`, `ForgotForm`, `RecoveryConfirmForm`, and the Security section content (`components/settings/sections/SecuritySection.tsx`, Plan 16a's placeholder). **No migration, no new dependency, no sessions table.**

**Tech Stack:** Next.js 16.4 App Router (server actions, `cookies()`), React 19.3, TypeScript strict, `@supabase/ssr` 0.12.7 + `@supabase/supabase-js` / `auth-js` 2.117.3 (already installed), next-intl 4, shadcn via the shared pieces (`Card`, `Input`, `Button`, `FormField`, `LoadingButton`), Vitest + Testing Library + jsdom. **New dependencies: none.**

**Spec:** `docs/superpowers/specs/2026-10-15-creator-toolkit-design.md` §0b ("change password (Settings → Security) and forgot/reset password via Supabase recovery email (needs custom SMTP + Site URL)"; round 4 had "Forgot-password email: skip for now", the owner has since asked for it: this plan supersedes that line), §7 ("Security (2FA, active session/sign out, password)"), `docs/TODO.md` §6b (both bullets). ## Supabase Auth calls this plan relies on (auth-js 2.117.3 in `node_modules`, docs read 2026-10-26)

| Call | Used for | Source | Verified how |
|---|---|---|---|
| `auth.resetPasswordForEmail(email)` | send the recovery email (no `redirectTo`: the template builds the link from the Site URL) | <https://supabase.com/docs/guides/auth/passwords> ("doesn't reveal whether an account exists"; PKCE example calls it without options) | docs + types |
| `auth.verifyOtp({ type: 'recovery', token_hash })` | exchange the emailed token for a session (server, cookie client) | same page (`/auth/confirm` + `{{ .TokenHash }}` template), `VerifyTokenHashParams` in `auth-js/dist/module/lib/types.d.ts` | docs + types |
| `auth.updateUser({ password })` | set the new password on the current session | same page | docs + types |
| `auth.signInWithPassword` on a separate `createClient(..., { auth: { persistSession: false, autoRefreshToken: false, detectSessionInUrl: false } })` | prove the CURRENT password without touching the cookie session | supabase-js reference | types; behaviour is an Open question |
| `auth.signOut({ scope: 'local' \| 'others' \| 'global' })` | revoke the check session / every other session / every session | <https://supabase.com/docs/reference/javascript/auth-signout> ("`others`: ends all sessions except the current one"; default is `global`; "There is no way to revoke a user's access token jwt until it expires") and `GoTrueClient.js` `_signOut` | docs + code read |
| `auth.getClaims()` → `claims.amr: { method, timestamp }[]` | "this session proved email possession in the last 15 minutes" | `JwtPayload.amr` in `types.d.ts` (`AMREntry { method, timestamp }`) | types; the method NAME for a recovery login is an Open question |
| error codes `same_password`, `weak_password`, `over_request_rate_limit`, `over_email_send_rate_limit`, `reauthentication_needed`, `otp_expired` | error mapping | `auth-js/dist/module/lib/error-codes.d.ts` | types |
| rate limits: `/recover` one per user per 60 s; emails 2/hour on the built-in mailer, adjustable with custom SMTP (project-wide); `/token` 150 per 5 min per IP; `/verify` 30 per 5 min per IP | what protects us beyond our cookie | <https://supabase.com/docs/guides/auth/rate-limits> | docs |

Not used, deliberately: `updateUser({ current_password })` (auth-js documents it only "when GOTRUE_SECURITY_UPDATE_PASSWORD_REQUIRE_CURRENT_PASSWORD is true"; whether the hosted dashboard exposes that switch, and what it does to the recovery flow, is unknown → Open question 4); `auth.reauthenticate()` (emails a nonce: not what "type your current password" means); any Admin API (no service role in auth flows).

**Every Supabase behaviour in the Open questions below is UNVERIFIED and has a live check in `docs/RUNBOOK_SECURITY.md` that must pass BEFORE the feature is relied on.** If a check fails, the failure mode is safe (see each question).
